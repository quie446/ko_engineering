# Reproducible Builds and Base Image Locking

`ko` can produce bit-for-bit reproducible images: the same module, the same
commit, and the same base image reference always yield the same image digest.
This page describes how to enable reproducible mode, how to pin base images
with a lockfile, and how to verify both in CI.

## TL;DR

```sh
# 1. Pin your base images to digests (commit the resulting ko.lock).
ko lock

# 2. Build reproducibly, using the locked base images.
ko build --locked --reproducible ./cmd/myapp

# 3. Verify in CI: lockfile is fresh and two builds produce the same digest.
ko lock --check
hack/verify-reproducible.sh ./cmd/myapp
```

Both modes are opt-in; without the flags, `ko` behaves exactly as before.
They can also be enabled via environment variables:

```sh
export KO_REPRODUCIBLE=true   # same as --reproducible
export KO_LOCKED=true         # same as --locked
export KO_LOCKFILE=ko.lock    # same as --lockfile
```

## What makes builds non-reproducible?

`ko` already normalizes most sources of nondeterminism by default: `kodata`
tar entries are written in sorted order with zeroed modification times, and
`-trimpath` is on by default. The remaining sources are:

| Source | Mitigation |
|--------|-----------|
| Base image tag moves (e.g. `:latest`) | `ko lock` + `--locked` pins the digest |
| Image config/history timestamps | `--reproducible` pins them to `SOURCE_DATE_EPOCH` (or the Unix epoch) |
| Go VCS stamping (dirty worktree changes the binary) | `--reproducible` adds `-buildvcs=false` |
| Go build ID | `--reproducible` adds `-ldflags=-buildid=` |

## Reproducible mode

`--reproducible` (or `KO_REPRODUCIBLE=true`) does the following:

- Pins the image creation time and `kodata` file timestamps to
  `SOURCE_DATE_EPOCH` / `KO_DATA_DATE_EPOCH` when those are set, and to the
  Unix epoch (`1970-01-01T00:00:00Z`) otherwise.
- Disables Go VCS stamping (`-buildvcs=false`), so an uncommitted change in
  the worktree does not change the resulting binary.
- Strips the Go build ID (`-ldflags=-buildid=`).

If you want timestamps to reflect a meaningful moment (e.g. the commit time)
instead of the Unix epoch, set `SOURCE_DATE_EPOCH` explicitly:

```sh
export SOURCE_DATE_EPOCH=$(git log -1 --format=%ct)
ko build --locked --reproducible ./cmd/myapp
```

Reproducible mode does not change your Go code or require any code changes;
it only affects how `ko` invokes `go build` and assembles the image.

## Locking base images

`ko lock` resolves the base images configured in `.ko.yaml`
(`defaultBaseImage` and `baseImageOverrides`) to immutable digests and
writes them to `ko.lock`:

```yaml
# This file is generated by `ko lock`. Do not edit by hand; run `ko lock` to refresh it.
version: 1
defaultBaseImage:
  ref: cgr.dev/chainguard/static:latest
  pinned: cgr.dev/chainguard/static@sha256:bf639cba19ba56329e6907ac26a7afcdde57a80b6aa66d5100da6883196e6b82
baseImageOverrides:
  github.com/acme/api:
    ref: distroless.dev/static:latest
    pinned: distroless.dev/static@sha256:...
```

Commit `ko.lock` alongside `.ko.yaml`. From then on:

- `ko build --locked` (or `KO_LOCKED=true`) resolves base images from the
  lockfile instead of the mutable tags, and fails if `.ko.yaml` has drifted
  from what was locked (run `ko lock` to refresh).
- `ko lock --check` re-resolves the configured references and fails with a
  non-zero exit code if the lockfile is stale — e.g. because a base image
  tag moved upstream or `.ko.yaml` changed without re-locking.

To update the base image deliberately, run `ko lock`, review the diff of
`ko.lock`, and commit. Rolling back is just `git revert` of that commit.

## Verifying in CI

### GitHub Actions

```yaml
name: reproducible-builds
on:
  pull_request:

jobs:
  reproducible:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod

      - name: Install ko
        run: go install github.com/google/ko@latest

      # Fail if .ko.yaml or the upstream base image moved without
      # refreshing ko.lock.
      - name: Check base image lockfile
        run: ko lock --check

      # Build twice with --locked --reproducible and compare digests.
      # Nothing is pushed; KO_DOCKER_REPO is only used to name the result.
      - name: Verify reproducible build
        run: hack/verify-reproducible.sh ./cmd/myapp
        env:
          KO_DOCKER_REPO: example.com/myapp
```

### Generic shell

The same flow works on any CI system:

```sh
ko lock --check
hack/verify-reproducible.sh ./cmd/myapp
```

`hack/verify-reproducible.sh` runs `ko build --push=false --reproducible`
twice (adding `--locked` automatically when a lockfile is present) and fails
if the two digests differ. Set `KO=/path/to/ko` to test a specific binary.

## Minimal reproduction recipe

To confirm reproducibility on a fresh checkout:

```sh
git clone <repo> && cd <repo>
git checkout <commit>
ko lock --check                                   # lockfile matches resolution
hack/verify-reproducible.sh ./cmd/myapp           # two builds, one digest
```

The printed digest is stable as long as the commit, the Go toolchain
version, and the locked base image digests stay the same.
